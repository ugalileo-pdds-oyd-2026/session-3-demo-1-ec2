## The application

The Go app is a minimal HTTP server with two endpoints. The same `main.go` runs on EC2, ECS, and EKS — the compute layer changes, the application logic doesn't.

```go
// main.go — buildHandler() registers routes and reads COMPUTE_TYPE from env
mux.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
    json.NewEncoder(w).Encode(map[string]string{
        "status":  "ok",
        "compute": compute,   // "ec2" when running on the instance
    })
})

mux.HandleFunc("/echo", func(w http.ResponseWriter, r *http.Request) {
    // reads JSON body, appends "compute" field, returns it
})
```

`server.go` has a `//go:build !lambda` build tag — it is compiled by default. `lambda.go` is only compiled when you pass `-tags lambda`. Both call the same `buildHandler()`.

### Compiling for Graviton2 (arm64)

The instance type is `t4g.nano` — Graviton2, ARM64 architecture. The binary must be compiled for that target from any machine:

```bash
cd app/
go mod tidy   # generates go.sum on first run

GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -o server .
```

- `GOOS=linux` — target OS is Linux (the instance), not macOS or Windows
- `GOARCH=arm64` — target CPU is Graviton2; an x86 binary won't run on t4g
- `CGO_ENABLED=0` — produces a fully static binary with no libc dependency; no runtime to install on the instance

The result is a single ~7 MB file. That is the entire deployment artifact.

## Infrastructure — Terraform module

### What the module creates

Six AWS resources, in dependency order:

```
aws_iam_role.instance
  └── aws_iam_role_policy_attachment.ssm   (AmazonSSMManagedInstanceCore)
  └── aws_iam_role_policy.s3_read          (s3:GetObject on the app bucket)
      └── aws_iam_instance_profile.this
aws_key_pair.ec2_key
aws_security_group.instance
    └── aws_instance.this
```

Terraform resolves this order automatically from the reference graph — you describe *what* depends on *what*, not the sequence.

### IAM: role, policy, instance profile

EC2 cannot assume a role directly. The required pattern is:

1. Create an `aws_iam_role` with `ec2.amazonaws.com` as the trusted principal
2. Attach policies to it (SSM for shell access, S3 for downloading the binary)
3. Wrap it in an `aws_iam_instance_profile` — EC2 requires this wrapper
4. Reference the profile name (not the role ARN) on the `aws_instance`

```hcl
resource "aws_iam_instance_profile" "this" {
  name = "${var.name}-${var.environment}-profile"
  role = aws_iam_role.instance.name
}

resource "aws_instance" "this" {
  iam_instance_profile = aws_iam_instance_profile.this.name
  ...
}
```

### Security group

Inbound: port 8080, TCP, from `var.allowed_cidr_blocks` only.
Outbound: unrestricted (needed for S3 access and `yum update`).

```hcl
resource "aws_security_group" "instance" {
  ingress {
    from_port   = 8080
    to_port     = 8080
    protocol    = "tcp"
    cidr_blocks = var.allowed_cidr_blocks
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

`allowed_cidr_blocks` has no default — the caller is forced to make a deliberate decision about who can reach the instance.

### SSH key pair

A key pair was registered with AWS so the instance could be reached over SSH if needed:

```hcl
resource "aws_key_pair" "ec2_key" {
  key_name   = "${var.name}-${var.environment}-ec2-key"
  public_key = file("${path.module}/key.pub")
}
```

The `key.pub` file in the module directory holds the public key. Note that in this demo the key pair is created but not attached to the instance (no `key_name` argument on `aws_instance`). Attaching it would enable SSH but also requires opening port 22 in the security group — that step was skipped to keep the surface minimal.

### User-data: bootstrapping the binary at launch

When the instance boots, EC2 executes the `user_data` script as root. This is how the Go binary gets onto the instance without baking it into the AMI:

```hcl
user_data = base64encode(<<-EOF
  #!/bin/bash
  yum update -y
  aws s3 cp s3://${var.app_s3_bucket}/server /opt/server
  chmod +x /opt/server
  COMPUTE_TYPE=ec2 nohup /opt/server &
EOF
)
```

`nohup ... &` starts the server in the background and detaches it from the shell session — the process keeps running after user-data finishes.

### Module variables

| Variable | Type | Default | Purpose |
|---|---|---|---|
| `environment` | string | — | Labels all resources (dev, staging, prod) |
| `name` | string | — | Base name prefix for all resources |
| `ami_id` | string | — | AMI to launch — region and arch specific |
| `instance_type` | string | `t4g.nano` | Must match the AMI architecture |
| `app_s3_bucket` | string | — | Bucket where the compiled binary lives |
| `allowed_cidr_blocks` | list(string) | — | Who can reach port 8080 |

AMI IDs are both region-specific and architecture-specific. Hardcoding one inside a module breaks it the moment a different region or architecture is needed. Exposing it as a variable makes the module portable and the constraint visible.

### Module outputs

```hcl
output "instance_id" {
  value = aws_instance.this.id
}

output "public_ip" {
  value = aws_instance.this.public_ip
}
```

The root `outputs.tf` proxies these as `compute_ec2_instance_id` and `compute_ec2_public_ip`.

## Running it

### 1. Upload the binary to S3

```bash
cd app/
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -o server .
aws s3 cp server s3://tito-terraform-demo-app/server
```

### 2. Initialize and apply Terraform

```bash
cd infra/
terraform init
terraform plan  -var-file=envs/dev/dev.tfvars
terraform apply -var-file=envs/dev/dev.tfvars
```

The instance is ready in ~30 seconds. User-data runs after boot — wait another 20 seconds for the binary to download from S3 and start.

### 3. Verify

```bash
INSTANCE_IP=$(terraform output -raw compute_ec2_public_ip)

curl http://${INSTANCE_IP}:8080/health
# {"compute":"ec2","status":"ok"}

curl -X POST http://${INSTANCE_IP}:8080/echo \
  -H "Content-Type: application/json" \
  -d '{"message":"hello"}'
# {"compute":"ec2","message":"hello"}
```

### 4. Destroy

```bash
terraform destroy -var-file=envs/dev/dev.tfvars
```

## Key concepts summary

| Concept | Why it matters |
|---|---|
| `GOARCH=arm64` + `CGO_ENABLED=0` | Static binary for Graviton2; one file, no runtime |
| Build tags (`!lambda` / `lambda`) | Same application code, different entrypoints selected at compile time |
| AMI ID as a module variable | AMIs are region and arch specific — hardcoding one breaks portability |
| `allowed_cidr_blocks` with no default | Forces a deliberate decision; a hidden `0.0.0.0/0` default is security debt |
| Instance profile ≠ IAM role | EC2 requires the profile wrapper; attaching the role directly is not supported |
| User-data for bootstrapping | Pulls and starts the binary at boot without baking it into the AMI |
| Terraform dependency graph | Resource creation order is resolved from references, not written explicitly |
